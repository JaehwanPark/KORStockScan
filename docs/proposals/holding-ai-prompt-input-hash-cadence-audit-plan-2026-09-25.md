# 보유 AI 프롬프트·입력·호출 주기 점검 계획 (2026-09-25)

## 목적과 현재 경계

[경로별 PASS/VETO 전환 계획](holding-ai-pass-veto-pre-signal-voting-plan-2026-09-25.md)의 **호출 생산자**를 점검한다. 대상은 Main SCALPING의 신호 전 `holding_path_vote` 단일 호출과 이 호출을 실제로 만들거나 막는 원천 조회, 검토 주기, 모델 전송, 응답 원장이다. 구 `holding_score`·`holding_flow`와 추가매수 재호출, 시뮬레이션·퇴역 경로는 활성 호출 여부를 census로 확인하고 활성 호출이면 중복과 의미 충돌을 결함으로 기록한다. 기존 SELL/ADD 신호, 경로별 복수 투표 집계, 안전 및 주문 권한은 이 점검의 결과만으로 바꾸지 않는다.

이 문서는 구현 및 배포 완료 영수증이 아니다. 현재 작업트리의 v9 구현은 미커밋이며 [재검토 영수증](../audit-reports/2026-09-25-holding-ai-vote-rereview-and-performance.md)에는 자연 투표 원장이 없다. 또한 2026-09-25 일일 checklist가 없어 당일 실행 소유자는 확인되지 않는다. 실제 적용 여부는 선택 release·설치 설정·PID 요청/응답 영수증으로 따로 대사한다.

## 1. 호출 경로·프롬프트 계약 점검

1. `sniper_state_handlers.py`의 모든 holding AI 호출 지점에서 `진입 후 보유 상태 → 호출 전제 → 요청 path ID → 프롬프트/스키마 → 응답 소비자 → 주문 영향` 지도를 작성한다. Main/다른 전략, 실거래/모의/퇴역을 분리한다. `is_sell_signal`이 참인 시점에 주기 검토가 생략되는 현재 전제가 경로별 첫 신호 이전 정족수에 미치는 영향을 실제 시각으로 측정한다.
2. 공통 프롬프트를 유지하더라도 **경로별 명세와 독립 판정 fixture**를 만든다. TP는 이익 보존과 후속 상승, soft stop은 손실 확대와 회복, post-add fail은 추가매수 후 실패, bad-entry는 진입 실패, rebound ADD는 추가매수 기대효과 및 별도 주문 안전을 평가해야 한다. 각 path의 `PASS`는 해당 신호/후보의 진행만 허용하고 `VETO`는 해당 경로의 한정된 보류/차단만 의미한다. 경로 간 표·근거 접두사·가격/수량/주문 명령이 섞이면 거절한다. 기계 신호가 아직 없는 것은 `INSUFFICIENT` 이유가 아니지만, 실제 판단 원천이 없으면 `INSUFFICIENT`다.
3. 세 시장별로 동일 입력의 의미와 필요 원천을 검증한다. 특히 NXT/통합애프터마켓 route·호가·체결·분봉의 시간 및 venue 정합성을 확인한다. 각 경로가 요청되는 **선행 시점**을 명시하고, 짧은 `POST_ADD_EVAL` 구간과 rebound ADD 전제처럼 2표를 모으기 어려운 경로는 호출 빈도를 올리기 전에 필요한 선행 원천/후보 상태가 있는지 확인한다.
4. 프롬프트 버전·실제 텍스트 해시·응답 JSON 스키마·의미 validator를 한 세대로 묶는다. `FIRM`/`TENTATIVE`, `reason_codes`, `input_insufficient`와 다중 경로 완전성을 검사한다. 입력에 없는 근거를 출력하거나 EXIT PASS를 ADD 허가로 해석하는 응답은 격리한다. 프롬프트는 English ASCII를 유지한다.

## 2. 경로별 입력과 해시 선행 게이트

1. 실전에서 만들어지는 입력을 `포지션/BUY 체결 세대`, `현재 quote·bid/ask·잔량`, `틱·분봉`, `flow/OFI`, `시장·세션·venue`, `원천 시각/품질`, `요청 path 집합`으로 펼쳐 **필드별 생산자→변환→전송값→응답/원장 소비자** 표를 만든다. 값의 단위, 미래 데이터 누출, REST/WS 혼합, 관측 시각 역행, partial candle, 빈 배열, 잘린 JSON, 이전 포지션 값 재사용을 점검한다. 필수 입력이 결손이면 해당 경로 표를 생성하지 않고 사유와 분모를 남긴다. 결손을 0·중립 점수·그럴듯한 AI 근거로 보충하지 않는다.
2. 해시를 목적별로 구분한다. `request_payload_sha256`은 실제 전송 JSON 전체를 감사용으로 고정한다. `decision_input_sha256`은 모델이 판단하는 정규화된 **실질 입력**과 요청 path 집합·포지션 체결 세대·시장·모델/프롬프트 버전을 묶는다. `path_decision_input_sha256`은 각 path ID와 그 경로에 쓰이는 실질 입력을 별도로 묶는다. 단순 조회 시각, 로그 ID, 전송 요청 ID처럼 매번 바뀌는 메타데이터만으로 판단 해시가 변하지 않게 한다. 반면 bid/ask/잔량, 새 체결·틱/분봉, 수익·고점·상태, 유효한 flow 변화는 반영한다. 정규화·숫자 정밀도·배열 순서·missing/null 구별을 버전으로 고정한다.
3. 호출 **전**에 같은 포지션·모델/프롬프트 세대의 마지막 요청 해시와 path별 마지막 요청 해시를 비교한다. 변화한 path만 요청 집합에 넣고 모두 동일하면 공급자 호출을 건너뛰어 `unchanged_input_skip`을 기록한다. 새 path가 활성화되었어도 변화 없는 기존 path는 재요청하지 않는다. 해시가 달라도 신선한 독립 시세 세대·경로별 preflight·공유 예산·단일 in-flight 조건을 모두 만족해야 예약한다. 같은 새 시세 세대에 변화한 여러 경로를 한 번에 묶되 같은 path의 같은 입력을 두 표로 세지 않는다. 프로세스 재시작 후에도 원장/호출 영수증으로 동일 입력을 재호출하지 않도록 한다.
4. 동일 해시 건너뛰기는 새 유효 표를 만들거나 이전 표의 최근성을 늘리지 않는다. 변화 없는 입력의 정상적인 skip 자체를 실패 표로 넣어 연속 구간을 인위적으로 끊지도 않는다. 원천이 오래 정지하면 그 자체를 `source_gap`으로 기록하고 기존 연속 투표는 나이·간격 제한에 따라 만료한다. 해시가 변했지만 실패한 시도는 실패/timeout/예산 거절을 별도 주기로 남겨 연속 집계가 결손을 숨기지 않게 한다. 리뷰 예정 시각, 실제 provider 제출/완료, 유효 표 저장 시각을 분리해 재시도 폭주와 부당한 쿨다운 연장을 모두 검증한다.

## 3. 모델·타임아웃·호출 빈도 실험

1. 요청 모델 설정의 단일 소유자를 정하고 시작 시점과 각 trace의 요청/응답 model ID, provider, prompt/schema 버전을 대사한다. 코드의 기본 문자열만으로 실운영 모델을 확정하지 않는다. [OpenAI 모델 문서](https://developers.openai.com/api/docs/models/gpt-5.4-nano)의 모델 지원 여부는 확인하되 계정/실제 PID의 응답 모델은 영수증으로 확인한다.
2. 동결 입력으로 원천 조회, 직렬화, 공유 lock/queue, HTTP 왕복, schema 검증, 파일 원장 저장 시간을 나눠 측정한다. 세 시장×경로 집합 크기·정상/부분/결손 입력과 다른 hot-path AI 동시 부하를 포함한다. timeout, rate limit, provider error, 프로세스 지연, 늦게 도착한 응답을 주입한다. deadline 뒤 응답은 새 표가 되지 않고 신호 시점에서 동기 AI 대기는 0이어야 한다. 7초 제한이 긴 리뷰 루프 정체를 유발하면 입력 축소·원천 재사용·비차단 실행·deadline 재설계를 먼저 검토한다.
3. 빈도는 현재 effective 주기와 공유 예산을 기준선으로 삼아 **후보 간격**을 여러 단계로 재생한다. 후보 선정 기준은 모델 이름이 아니라 `새 실질 입력 생성률`, `요청 성공률`, `신호 전 2표 이상 성숙률`, `표 최신성/최대 간격`, `p99 지연`, `종목·계정 전체 요청/분`, `입력/출력 토큰과 원가`, `entry 등 다른 AI의 예산 손실`, `이후 비용 후 경제성`이다. 입력이 그대로면 최대 쿨다운이 지나도 같은 입력으로 투표를 늘리지 않는다. 공유 예산 변경은 entry/holding/ADD 서비스 비율과 보호 우선순위를 함께 검증한다.
4. `gpt-5.4-nano`의 최종 v9 표본은 기존 영수증상 1회뿐이므로 p99·timeout 0·고빈도 안정성을 주장하지 않는다. 먼저 독립 날짜의 무주문 동결 데이터와 제한된 실제 요청으로 지연/출력 유효율을 추정한다. 신호 전 표 부족의 원인이 느린 모델인지, 빈번하지 않은 입력인지, 원천 preflight·단일 lock·공유 예산·경로 활성화 지연인지 분해한 뒤 호출 간격을 선택한다. 필요한 속도가 실제 응답 분포와 안전 deadline을 함께 만족하지 못하면 해당 셀은 `INSUFFICIENT`로 남긴다.

## 검증 자료·산출물·완료 기준

- 실제 시점별 source/position/BUY 영수증과 prompt에 전송된 요청/응답 trace를 세 시장×각 활성 경로로 동결한다. 입력 복원이 불가능한 과거 건은 결손 표본으로 남긴다. 구 점수 답변을 정답으로 쓰지 않는다. 사용자 데이터와 공급자 trace는 민감정보를 가린 검증 복사본으로 다룬다.
- 경계 fixture: 동일 입력에 새 timestamp만 추가, 새 generation이나 같은 실질 호가, bid/ask만 변화, 틱/flow만 변화, path 집합 전환, 시장/포지션/부분 BUY 체결 전환, stale·future quote, 0/1/2 독립 표, timeout·late response·lock contention·budget 거절·재시작. 기대값은 호출 0/1회, path별 유효 표 수, 이유, 신호 시점 결정을 고정한다.
- 보고서는 경로×시장별 `검토 대상 → 원천 적격 → 입력 해시 변화 → 예약 허용 → 요청 → 정시 응답 → schema/의미 유효 → 원장 저장 → 첫 신호 전 정족수` funnel과 제외 사유를 표기한다. 중복 입력 호출 0건, 같은 입력으로 중복 표 0건, 모델 불일치 유효 표 0건, 신호 뒤 소급 표 0건, 신호 시점 동기 모델 호출 0건을 기능 수용 기준으로 삼는다.
- 성능 보고서는 단계별 p50/p95/p99/최대·timeout/오류율, symbol·전체 호출량, 토큰/비용, 원장 I/O, 루프 지연, 공유 예산으로 놓친 entry/holding 기회를 포함한다. 후보 간격별 신호 전 정족수 성숙률이 개선되어도 source/안전 품질이나 다른 호출을 악화시키면 적용하지 않는다. 자연 완료·비용 증거가 없으면 경제성은 `null/source_gap`; 빈도·프롬프트 변경의 자동 실거래 선택 근거로 삼지 않는다.
- 실행 순서는 **호출 census와 실제 모델 대사 → 경로별 프롬프트/입력 계약 → 이중 해시·선행 중복 게이트 → 단계별 deadline/지연 계측 → 공유 예산 포함 빈도 실험 → 코드리뷰·수정·재리뷰·대상 검증 → 별도 release/PID·자연 표 수용**이다. 코드 변경이 시세 REST/WS parser나 요청 의미에 닿으면 당시의 공식 Kiwoom 참조 gate를 먼저 수행한다. 배포·호출 주기 변경·자연 수익성은 각각 별도 결과로 보고한다.
