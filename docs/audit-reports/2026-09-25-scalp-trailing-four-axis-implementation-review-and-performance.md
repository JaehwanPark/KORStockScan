# 스캘핑 트레일링 4축 구현·리뷰·실행 성능 기록

기준: 2026-09-25 KST 작업본. 이 기록은 코드·읽기 전용 계산 검증이며 선택 release, 실제 PID, 정책 적용 또는 자연 수익을 증명하지 않는다.

## 구현 범위와 리뷰

- `src/engine/scalping/trailing_threshold_policy.py`가 4축×3시장 값·출처·단일 vector hash와 명시적 다음 날짜 선택 영수증 계약을 소유한다. Bootstrap v3은 12개 키를 공급·검증하고 부모 rollback hash, 원천 보고서 hash, 운영자/lock 충돌을 대사한다.
- fast/normal 익절은 같은 평가 시각 시장 벡터를 쓴다. normal의 후행 호가 복구 재평가에서도 시장별 익절 폭을 유지한다. 손절 동적 stop 소비는 별도다. 점수 TTL·source·quality·효력 시각, peak/bid/잔량과 정책 vector가 전이에 남는다.
- 트레일링 관측은 시작/되돌림/점수의 격자 경계를 넘는 평가를 남긴다. 폐장 동안의 평가 공백만 공통 `session_contract`로 확인해 허용하고 arm 상태를 다음 거래 가능 구간으로 넘긴다. cap·시계·원천 결손은 해당 ID를 격리한다.
- `trailing_four_axis_replay.py`는 엄격 완료 projection을 입력으로 한 4축 단일·다섯 쌍·학습 구간 봉인 최대 81 조합·최종 3시장 최대 27 벡터의 보고 전용 재생을 구현했다. 다른 청산을 포함한 비용 후 paired 손익, 검열, 공통/후보별 ID, train/holdout, 손실 악화를 분리한다. 시작값의 기존 시장 전체 차단 조건은 ID별 제외로 고쳤다.
- 회귀 첫 실행에서 후보별 공통 분모를 전원 교집합으로 처리해 정상 행까지 `excluded_ids`에 넣는 결함, 기존 rising-missed 검증 오류 라벨 변경, 부분 매도보다 앞선 실제 종료 시각 누락, 장 경계 공백, 재생 소스 TTL 검증 누락을 확인해 수리했다. 후속 재리뷰에서 후보별 적격 ID가 다른데도 각각의 EV를 비교하던 결함을 찾아 시장별 전체 후보와 최종 3시장 후보의 집계 분모를 각각 공통 ID로 고정했다. 과거 기준 벡터가 달라 강폭≥약폭을 깨는 단일·쌍 조합은 결손 표본으로 넣지 않고 무효 후보로 분리했다. 후보별 개별 적격·검열 ID는 별도로 남긴다. 전용 start↔4축 parity, 캐시↔새 전처리 parity, 정책 tamper/부모 hash, 폐장 경계·공통 분모·무효 폭 회귀를 추가했다.

## 측정

기존 wrapper 기본 timeout은 `deploy/run_monitor_snapshot_safe.sh`의 `MONITOR_SNAPSHOT_TIMEOUT_SEC=1200`초다. 성능 예산을 **구현 전 별도 봉인한 영수증은 없다**. 아래 결과를 timeout 대비 수용 PASS나 자연 운영 여유시간 증명으로 부르지 않는다. 합성 입력은 동일 머신의 일관된 10일 train/holdout, 한 시장 정규장 경로와 실제 비용을 흉내 낸 행으로 계산했다. 3시장 값은 계산했지만 노출 시장은 정규장 하나라 최종 결합 후보는 3개였다. 가격·성과는 합성이며 정책 근거가 아니다.

보존일 읽기 전용 순차 계측 합계는 약 131.3초다. `trade_review` 재계산 결과를 저장하지 않아 뒤 단계는 같은 새 세대가 아닌 기존 영수증을 읽었다. `post_sell_feedback`도 API 재평가를 실행하지 않았다. 따라서 이 합계를 실제 strict handoff 완료시간으로 쓰지 않는다. 실제 보존일의 4축 적격이 0건이므로 1.74GB 보고서 RSS는 주로 기존 장후 입력/빌드 비용이며, 합성 4축 327MB를 더한 값을 자연 피크라고 단정하지 않는다.

## 잔여 수용

- 현재 `session_contract`는 `PREMARKET` 08:00~09:00의 `exit_allowed_by_clock=false`다. 세 정책 시장은 유지하지만 프리마켓 익절 신호·최적값은 현행 계약에서 식별할 수 없다. 거래 가능 시간이 공식적으로 바뀌기 전까지 임의의 프리마켓 익절 표본을 합성하지 않는다.
- 9/23 자료는 엄격 완료/시각순 원천이 0건이다. [과거 원천 조사](2026-09-25-scalp-trailing-four-axis-historical-source-availability.md)의 ID 결손을 복원하거나 새 자연 완료·비용 표본을 확보한 뒤 경제성 후보를 판단한다.
- 3시장 모두 노출되는 자연 입력, 주문 실패·슬리피지 보수 하한, 동일 세대 전체 stage·strict handoff 시간, 실제 PID 소비와 적용 후 비용 후 효과는 별도 검증 대상이다. 보고서의 `research_candidate`나 합성 표본 후보는 live 적용 권한이 아니다.

## 9/25 추가 재리뷰: 실행 가능 수량·비용 민감도·검열

- [`trailing_start_replay.py`](../../src/engine/scalping/trailing_start_replay.py)는 전이마다 최우선 bid 수량이 양의 정수인지 검증한다. 값이 없거나 무효면 가격 경로를 적격으로 통과시키지 않는다.
- [`trailing_four_axis_replay.py`](../../src/engine/scalping/trailing_four_axis_replay.py)는 후보 첫 trigger bid 수량과 실매수 체결수량을 비교한다. bid가 일부 수량만 받칠 때 해당 일부의 가정 proceeds/basis와 잔량을 출력하고 전체 paired PnL은 `censored_insufficient_trigger_bid_depth`로 검열한다. 결손 잔량을 0원이나 전량체결로 처리하지 않는다. 충분한 top-bid 수량이 확인된 앞당긴 후보에는 0/30/100bp 매도 슬리피지 민감도를 추가한다. 이는 가격 민감도 모형이며 체결 영수증이 아니다.
- 후보 정책 선택 경계는 최신 holdout에서 날짜별 최악 슬리피지 EV와 검열·비대응 notional을 반영한 최악 슬리피지 손익이 양수인지 확인한다. 해당 증거가 없거나 0 이하이면 [`trailing_threshold_policy.py`](../../src/engine/scalping/trailing_threshold_policy.py)의 선택 검증이 거부한다. 실측 슬리피지 상한을 의미하지 않는다.
- 실행 후보가 실제 take-profit 신호보다 늦거나 관측 잔량으로 수량을 다 팔 수 없으면 검열 ID와 원인을 남긴다. bid 잔량 결손은 source gap으로 구분한다. 첫 실패 때 정책 선택 fixture가 새 holdout 비용 증거를 포함하지 않아 테스트가 실패했고, fixture/검증 계약을 보완한 뒤 통과했다. 후속 재리뷰에서 민감도 딕셔너리가 불필요한 행마다 복제되는 점을 확인해 내부 tuple 표현 및 필요 시점 생성을 적용했다.

### 수정 후 계산 계측

동일한 합성 입력을 크기별로 같은 프로세스에서 두 번 재생했다. 모든 포지션은 REGULAR에 노출되며 PREMARKET/통합 AFTERMARKET 노출은 0이다. 보고서 hash, 적격 분모, 후보 수가 반복 간 일치했다. 원천 파일 I/O·API 호출·주문은 없었다. `max RSS`는 합성 입력 객체와 산출물을 포함한 프로세스 최고치이며 이 재실행에서는 swap을 별도 측정하지 않았다.

| --- | ---: | ---: | ---: | ---: | --- |

| 1,000포지션×40전이 | 44.467 / 44.437초 | 44.465 / 44.432초 | 436.7 / 436.8MB | 1,000 / 3 | `72380d3e9fff2b0c2d0ec9c7ef99b096a21f983667ce8bc80babaa6d61aee8` |

행별 민감도 딕셔너리를 저장한 첫 재실행은 최대 RSS가 각각 420.1MB와 643.1MB였다. 같은 입력 builder·재생 호출에서 tuple/cache 개선 후 각각 351.7MB와 436.8MB로 내려갔고 반복 hash는 일치했다. 실행 시간은 사실상 같았다. 이 계측은 합성 계산만 확인한다. 9/25 보존 census는 엄격 4축 적격 0건이며 실제 3시장 경로·체결 민감도는 계측하지 못했으므로, 경제성이나 전체 장후 시간 예산 수용으로 해석하지 않는다.

최종 position-key 검증을 포함한 코드에서도 엄격 완료 입력을 실제로 통과시키는 별도 sparse-score-grid 합성 재측정을 했다. 앞 표의 3 joint 후보 생성용 score 분포와 다르므로 처리시간을 직접 비교하지 않는다. 두 재측정 모두 원천 공백 0, 실제 벡터 1개, REGULAR 노출만 있었고 PREMARKET/통합 AFTERMARKET은 0이었다.

이 추가 계측도 합성 한 시장·한 score 값이며, 반복 해시 비교와 프로세스 swap 계측은 하지 않았다. 기존의 동일-input 반복 해시 결과는 위 표의 tuple/cache 버전 측정으로 남긴다.

### 검증

수정 후 관련 report/replay/bootstrap 범위 pytest는 `66 passed`; ruff, compileall, `git diff --check`도 통과했다. 최종 DB 거래 ID 연결 검증은 성능 경로에 O(전이 수) 선형 검사만 더하며, 아래의 최종 코드 측정에서 같은 입력 적격 분모와 반복 hash가 유지되는지 재확인한다. 전체 장후 snapshot은 다시 생성하지 않았다. 보존자료의 strict 0건·미완료 census, 저장 보고서의 hash, 선택 릴리스, 실제 PID 상태는 이 작업으로 변경되거나 새로 증명되지 않는다.
