# Main runtime release routing

Owner: deployment infrastructure. Installed main routing is separate from exact-date trading approval. Widget/episode services use the separately authorized machine pin described below, not the main selector.

## 스캘핑 트레일링 익절 기계판정 영수증

강약 폐루프 v2는 `SCALP_TRAILING_START_PCT`, `SCALP_TRAILING_LIMIT_WEAK`, `SCALP_TRAILING_LIMIT_STRONG`의 3시장 9값과 `mechanical_strength_v2`의 3시장×8개 분류값을 한 `KORSTOCKSCAN_SCALP_TRAILING_MECHANICAL_VECTOR_SHA256` 영수증으로 묶는다. `book_cutoff`는 소비하지 않는다. `SCALP_TRAILING_STRONG_AI_SCORE` scalar는 soft-stop 소유자로 남고 익절 강약에는 쓰지 않는다. 구 4축·시장별 AI 점수 override·v1 선택 영수증은 v2 후보로 재적용하지 않는다. fast/normal은 같은 시장 수익값·분류값을 소비하며, 프리마켓의 청산 가능 여부는 평가시각의 실제 적용 `session_contract`로 판정한다.

장후 wrapper는 최종 `trade_review → post_sell_feedback → holding_exit_observation`을 `postclose_exit` profile로 다시 생성하고 세 파일의 SHA256 manifest를 `runtime_approval_summary` 전에 검증한다. `trailing_mechanical_market_tuning`과 분류기 연구 자체는 보고 전용이다. M1 첫 관측 진입일 이후의 완료 census를 별도 모수로 봉인하며, 이전 구세대의 미봉인 날짜가 새 모수를 영구 차단하지 않게 한다. 해당 M1 기간의 누락 날짜·미배치 ID는 차단한다. 다음 PREOPEN의 `scalp_trailing_mechanical_policy_apply`만 source date/profile/hash·완료 비용 모수·독립 날짜·보수 비용·한 시장 canary·부모 hash를 검토해 결합 정책 v2 후보 영수증을 만든다. 표본·edge 결손은 hold/carry, 변조된 선택 영수증은 bootstrap에서 차단한다. 선택된 시장별 시작값과 강약 설정은 무후보 날짜에도 같은 hash로 유지하며 명시적 운영 변경 시 귀속을 분리한다. 운영자 override/lock 우선순위와 단일 stage 규칙은 유지한다. Bootstrap 생성·검증, 선택 릴리스, 실제 PID 소비, 자연 완료 비용 후 성과는 별도 영수증이다.

## Single selection

`data/runtime/runtime_release_selection.json` selects one absolute managed release root and its full Git commit. The workspace entrypoint is `bash deploy/run_runtime_release.sh`. It checks the selected HEAD, clean `src/deploy/restart.sh` and shared `data/logs/tmp/.venv/docs/restart.flag` before invoking a target. Missing or invalid selection blocks execution; it must not fall back to mutable workspace code.

The canonical workspace `restart.sh` delegates to this entrypoint. The reviewed release's original `restart.sh` preserves its policy code pin and custody-aware restart procedure, and its post-restart PID check uses `automation.runtime_policy_bootstrap --write-verify-artifact`; the retired generic apply module is not a valid verifier. Do not call old release restart scripts or workspace `src/run_bot.sh` directly to choose a deployment. Do not edit or pull inside the selected release.

## Cross-session deployment gate

Before a coordinated release transition, run `bash deploy/run_runtime_release.sh --check-release-set`. The configuration-read-only check serializes against transitions, validates the selected main release, and inventories the widget trader, episode expander, and loaded low-price live/preflight instances. It creates only the shared lock file when absent. The inventory is capped at 256 units and the per-unit check has a 30-second total deadline. Each owner may keep its separately approved release commit; the check verifies its managed root, effective command/workdir agreement, runtime commit pin when present, and every configured policy path/hash pair. Git-backed releases must have clean runtime source; exports without `.git` require the unit's full commit pin to match the release-directory hash suffix, while source cleanliness remains unverified. Its PASS covers deployment routing only (`functional_runtime_health=not_assessed`); the current main PID receipt is reported separately. A running PID's actual policy consumption, natural functional acceptance, and economic results remain separate evidence; loaded failed/inactive units are reported separately and are not silently called healthy.

The main `start`/`restart` transition, cron installation, and every repository systemd installer/uninstaller use the same nonblocking `data/runtime/runtime_release_set.lock`. If it is held, the competing transition fails before changing an owner. Repository installers acquire it themselves; do not wrap one in another lock. For a manual selector publication or out-of-band systemd change, hold it with `bash deploy/with_runtime_release_set_lock.sh <command>`; this also takes the PID-receipt selection lock so an atomic selector write cannot overwrite a concurrent receipt. PID-receipt writes use that selection lock and revalidate the selected root before replacing the manifest. This cannot coordinate edits made outside the wrapper, so release selection and owner configuration must be changed only through these guarded paths. A release transition still changes only the explicitly named owners; do not restart widget or episode machines as a side effect of a main-only update.

Supported operations: `start`, `restart`, `preopen`, `postclose`, `paired-replay`, `controller`, `tuning`, `finalize`, `eod`, `archive`, `buy-funnel`, `holding-exit-sentinel`. Intraday holding-exit sentinel cron uses `holding-exit-sentinel` so its report code follows the selected release. Invocation resolves the selection once and pins `PROJECT_DIR/PYTHONPATH/VENV_PY` for its child chain. The selector does not update an already-running supervisor; moving the current PID requires a separately authorized graceful restart.

Read-only checks from the canonical workspace:

```bash
bash deploy/run_runtime_release.sh restart --print-plan
bash deploy/run_runtime_release.sh preopen 2026-09-11 --print-plan
bash deploy/run_runtime_release.sh --check-cron
```

Use the actual target date instead of the example. A plan check proves routing, not future policy approval, WS health or a running PID.

## Scheduled scope and maintenance

Eight cron entrypoints use the selection: 07:35 PREOPEN, 07:55 main start, 20:05 EOD, 20:10 postclose/controller/tuning, 20:50 archive and 21:55 finalization. The 21:05 paired replay wrapper is manual compatibility; the main wrapper owns the current auxiliary calculation. The cron check requires all eight installed owners. Existing schedule, environment values, log ownership/redirection and wrapper locks are preserved. Existing 07:30/20:10 stop behavior is unchanged; routing is not a redesign of shutdown semantics. Other intraday observer/scanner jobs and machine systemd services remain outside this scope.

After an authorized cron installer is run, check routing again: older installers can recreate workspace entrypoints. `bash deploy/run_runtime_release.sh --install-cron` reconciles exactly these eight rows, preserves unrelated rows and leading environment/log redirections (including main start), creates before/after backups in `tmp/runtime-release-cron-*`, rejects missing/duplicate/unrecognized commands and verifies readback. It recognizes an actual command owner, not an echo/printf/conditional containing the route. Scheduled `--print-plan` and unexpected extra arguments are rejected; dated jobs retain the existing KST cron date expression. Unsupported command syntax requires review, not an automatic rewrite. `--check-cron` only reads the current snapshot and does not create or wait on an installer lock. Installation uses a nonblocking lock; do not run it concurrently with another crontab editor. Direct out-of-band edits after its final recheck cannot be atomically prevented by the crontab interface.

For a release update: review and test only intended changes in a separate worktree, commit that release, mount shared state/docs, verify dated code/source pins, then atomically replace the selection file with the approved exact root/commit. Never switch while scheduled wrappers are running: separately started followers could otherwise select different releases. Keep the prior release and selector record for rollback. Do not erase data, reset quota or change policy to make a route pass. Shared `.venv` means dependencies are not immutable; package changes need their own approval and validation.

Restoring a cron backup is appropriate only after checking for subsequent unrelated edits; never overwrite a newer crontab wholesale. Rollback selection requires the prior release to pass the same shared-path and source checks, including the shared `docs` contract. Merely reverting a commit string is not enough.
