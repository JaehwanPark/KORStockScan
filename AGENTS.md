## 2. Decision Principles

- The goal is not loss suppression, but expected value and net-profit maximization.
- The Plan Rebase period baseline is `main-only`, `normal_only`, and `post_fallback_deprecation`.
- The tuning data decision baseline is `2026-06-05T00:00:00+09:00 KST`; pre-baseline raw/report/analytics data is forbidden for current tuning decision inputs and remains archive/audit evidence only.
- Live changes allow only one canary axis within the same stage. Stage-disjoint concurrent canaries can be reviewed in parallel only when stage, manipulation point, apply timing, cohort tag, and rollback guard are separated, such as entry-bottleneck versus holding/exit axes.
- New or supplemental alpha tuning axes are treated as `canary-only` without shadow. Operational/support axes explicitly documented as observe/report-only, such as AI transport/schema, statistical action weight, and decision matrix, must not change real order or exit decisions.
- Remote comparison values are excluded from Plan Rebase decision inputs.
- Profit/loss uses only `COMPLETED + valid profit_rate`. Exclude `NULL`, incomplete, and fallback-normalized values from PnL criteria.
- Do not merge `full fill` and `partial fill`.
- Win rate is a supporting diagnostic; EV primary metric owns expected value and net-profit decisions.
- Daily-only metrics may be used for safety/source-quality/operational triggers, but live/canary/threshold apply approval must use rolling/cumulative or post-apply version windows as well.
- Tuning performance reports must separate identification/source quality, code review, actual policy/PID consumption and remaining economic acceptance. Sim application is relevant only for surviving enabled sim owners; do not require retired LDM/bucket consumers. For any blocker, name the exact owner artifact, observed evidence, next repair or natural acceptance and closure test.
- Split post-BUY non-entry into `latency guard miss`, `liquidity gate miss`, `AI threshold miss`, and `overbought gate miss`.
- If attribution is unclear, check report consistency, event reconstruction, and aggregation quality before changing strategy thresholds.
- Operational automation evidence such as cron, runbook, manifest, report, and parser normalization is separate from strategy effect or live approval evidence.
- When possible, structure answers as `decision -> evidence -> next action`.

## 5. Codebase Work Review And Fix Loop

- Every codebase modification must close through `implementation -> self code review -> supplemental fixes -> revalidation -> result report`.
- After any KORStockScan codebase modification, use `$korstockscan-review-gate` as the default review gate when the skill is available. The gate must repeat `review -> fix defects -> re-review -> targeted validation` until there are no unresolved findings before final reporting.
- Do not restart the bot, regenerate expensive reports, or run broad automation after a code change until `$korstockscan-review-gate` has closed with no remaining defects, relevant targeted validation has passed, and the user or runbook/checklist explicitly allows that runtime follow-up.
- Before creating or moving a source file, package, CLI module, report producer, or test, enforce a mandatory location gate. `src/engine` root is closed to new Python modules by default; new `.py` files there are allowed only when the engine-root allowlist test is deliberately updated in the same change with a written ownership reason. First inspect the repository structure and nearby producers/consumers, then choose the directory that matches the work's role: live engine/runtime, swing dry-run/simulation, scanner, model/training, report producer, test, document, or offline/archive analysis. Prefer existing role packages such as `src/engine/automation`, `src/engine/swing`, `src/engine/scalping`, `src/engine/lifecycle`, `src/engine/monitoring`, `src/engine/risk`, `src/engine/error_detectors`, `src/engine/infrastructure`, or `src/engine/ai` over a root-level module. If multiple locations look plausible, state the chosen ownership boundary and keep compatibility wrappers only when an existing caller or documented command requires them. Wrapper modules must be temporary compatibility surfaces, not a way to leave duplicate implementation residue.
- Self-review must not stop at skimming changed files. Also check the changed path's producer/consumer contracts, silent-fail possibilities, runtime/order/provider/threshold authority leaks, and regressions existing tests may miss.
- Fix issues found during review immediately, without waiting for the user to separately ask for supplementation. If the fix scope goes beyond the original request or leads to runtime/order/provider/bot/threshold changes, separate the scope and report it first.
- After supplemental fixes, run relevant targeted tests, syntax/compile checks, and `git diff --check` by default. Include parser validation for document/checklist/parser changes.
- If tests were not run or only partially run, state why and name the remaining risk in the final response.
- Simple lookup, explanation, and no-code review requests are exceptions. Once code or automation files are modified, this loop applies.
