- Maximize expected value and net profit under Plan Rebase's family contracts. Baseline: `main-only`, `normal_only`, `post_fallback_deprecation`. Remote comparison values are excluded.

Win rate is diagnostic; live approval also needs rolling/cumulative or post-apply version evidence. Preserve approved overrides, expiry and custody boundaries.
- Attribute post-BUY non-entry to `latency guard miss`, `liquidity gate miss`, `AI threshold miss` or `overbought gate miss`; repair source consistency before tuning thresholds.
- Preserve Main/manual custody, historical owner receipts, operator vetoes and hard safety. Episode/widget automatic BUY/SELL/CANCEL/retry, workers, UI, collection, research and publication are permanently retired. Their holdings are operator-managed: Main must not adopt or sell them, residual quantities/intents do not block Main, and retired-owner flat reconciliation is not required. Review producers/consumers, silent failures, missing/stale inputs and authority leaks. Fix in-scope findings; report a mutation requiring new authority before making it. - Before creating/moving code or tests, inspect nearby owners. Prefer existing role packages; `src/engine` root is closed to new Python modules by default. Exceptions require an intentional engine-root allowlist test update and written ownership reason. State ambiguous location ownership. New modules, report producers and validators must explain why an existing owner cannot be extended or reused.

- Remove displaced implementations, stale registrations/call sites and duplicated checks in the same scoped change once consumers migrate. Inspect dynamic imports, CLI/shell callers and relevant registry/schedule entries; text-search absence alone is not proof. Moves, OFF flags or extra wrappers alone are not removal. Wrapper modules must be temporary compatibility surfaces, forwarding to one implementation only while a named caller/command requires them.
- Retained code needs a current consumer and reason. Temporary compatibility/deferred removal also needs an owner, checkable removal trigger and closure test under the existing checklist ID. Preserve necessary historical readers/evidence and immutable releases, not retired trading authority. In-scope duplicates or unexplained old paths block removal completion. A documented external dependency may close the functional repair with removal explicitly deferred; it grants no deployment/cleanup authority.
- Record baseline commit/scope and additions/deletions separately for non-test source, tests and docs; distinguish moves and unrelated changes. Explain net growth and changes in owners/branches/entrypoints. No negative-line quota: new capability may need code, but moving/minifying is not simplification. Reuse fixtures/parameterization while preserving distinct failure coverage; do not add validators solely to enforce this rule.
- Run `git diff --check`; Python changes use relevant pytest and compile checks, wrappers use `bash -n` and affected contract tests. Separate code review, deployment, natural generation, selection, exact-date policy/PREOPEN/PID consumption and cost-adjusted economics. Reopen completed work only for new defects, changed contracts or mandatory handoff failure; absent samples alone do not reopen code cleanup.

## 6. Error Resolution Procedure

An error-fix request follows this procedure within its authorized scope, including when the same alert returns. Editing these rules does not invoke repairs or runtime actions. Temporary containment must name its owner, expiry/removal trigger and remaining causal repair; it is not root-cause closure.

1. **Pin the incident.** Record the failing command/check, expected versus actual result, first failure/last valid evidence, affected date/scope/IDs and source generation. Verify the actual producer, consumer, selected release and relevant PID/start ticks; distinguish old-release alerts from current failures. Preserve original failure bytes and attempts. Group causally related alerts under the existing checklist owner without merging distinct failures or losing their identities.
2. **Prove the first broken contract.** Trace the actual path from collection/trigger through queue, writer, parser/index, publication and consumer to the detector. Identify the responsible file/function/predicate and why the invalid state was produced or accepted. Use a bounded reproducer, existing regression test or exact failure evidence to test the causal hypothesis; an alert string or downstream exception alone is not a root cause. Mark unproved hypotheses explicitly and continue diagnosis instead of changing unrelated code.
3. **Classify before repairing.** Separate an active producer/consumer failure, a detector misclassification, expected wait/valid-empty/guard behavior, and irreversible historical loss. Check the owning contract's scope and deadline. Missing evidence is neither zero economics nor success; exclusions contain invalid rows but do not fix the code that keeps creating them. A detector defect requires correcting its contract interpretation, not altering valid production data to satisfy it.
4. **Repair the existing owner.** Fix the earliest violated contract and affected direct consumers, covering both the failing instance and future inputs on the same path. Inspect shared callers, retries, partial writes, caches and generation transitions where relevant. Follow §5 to remove displaced paths/checks; do not add another wrapper, validator, report or fallback merely to bypass the defect. Manual artifact/status/hash edits, forced DONE, stale PASS reuse, broader exception swallowing, warning suppression or guard/timeout/size-limit relaxation alone are not repairs.
5. **Bound recovery and resource work.** Before a rerun, name what changed, which evidence it can recover, the minimal dependency range, and its stop/progress condition. No unchanged full rerun or endless retry after the same deterministic failure or irreversible loss. When source growth/read volume/backlog is causal, repair the existing writer-to-index/checkpoint/manifest-to-consumer path for future data as well as existing data; use verified incremental or bounded reads with identity/coverage validation. Check bytes read, input growth versus processing throughput, lag and relevant I/O/CPU/memory evidence. Repeated whole-source scans/hashes or larger budgets alone do not establish scalability. Necessary one-time migration uses an explicit bounded, resumable plan under existing authority.
6. **Review and validate the cause.** Apply §5's review/fix/re-review loop. For code repairs, preserve a regression that fails for the original defect and passes after the fix, plus relevant negative cases proving that missing/stale/conflicting/new-generation inputs and hard guards still behave correctly. Use existing fixtures and mocked/offline validation; no live provider/order calls for a test. Verify the affected producer and consumer together, not only the helper or alert formatter. Document-only changes retain document-only validation.
7. **Close through actual consumption.** After review and within existing authority, regenerate only invalidated dependencies in order, validate native semantics/date/scope/hash, then verify the intended last consumer and original failing check. Use the intraday/postclose instructions and release-routing contract for their specific closure. Exit zero, publication, alert absence or restart alone is insufficient. Report code closure, artifact recovery, deployment/PID consumption and next natural-window verification separately; pending authority/evidence stays with its owner and checkable next action. Do not impose unrelated fills, positive EV or promotion floors on a diagnostic repair.
8. **Handle recurrence without hiding failures.** An immutable, irrecoverable historical gap may remain excluded/null with exact IDs, reasons and source hashes under its native contract; move it to historical diagnostics only after the affected current producer/consumer contract and that classification are verified. Test both the historical classification and continued detection of new loss/current failures; invalidated bindings and unknown provenance remain actionable. Deduplicating unchanged notifications is separate from resolving the incident: retain the active failure, owner and next action, and surface changed impact or failed recovery through the existing monitor contract. Recurrence of the current defect reopens the causal hypothesis or failed acceptance under the same owner; an unchanged historical exclusion does not. Do not repeat the previous workaround or create a parallel tracking framework. Record `cause -> repair -> regression -> consumer evidence -> residual loss/next action` in the existing review/checklist, identifying the contract that prevents recurrence in future inputs and any still-unproved acceptance.
